# Milestone 49: Test determinism (robust readiness and outcome waits)

Status: planned. It makes the smoke suite report only real failures, so it is
Milestone 49 in the project sequence. The suite has grown to 454 checks across dozens
of milestones, and M48 was itself a milestone to fix a test that flaked. This
milestone removes the timing fragility that let a slow moment on the machine look like
a code failure.

## Goal

The harness has two kinds of wait and both cap at the same three seconds. A readiness
gate waits for a server to boot and a session to connect before the block's commands
run; an outcome check waits for a specific game result to appear in a log. A readiness
gate that gives up proceeds anyway with an empty session id, so every command in that
block fails, turning one slow boot into a cluster of false failures. An outcome check
that gives up reports a single false failure on a result that was merely late. Neither
distinguishes "not ready yet, wait longer" from "genuinely wrong", so a loaded machine
can fail a run whose code is correct.

This milestone makes the waits robust: readiness gates wait long enough and fail loudly
and singly when a server truly does not come up, and outcome checks wait long enough
that a slow-but-correct result is not a false failure. Because a poll returns the
moment its condition is met, a healthy run is unchanged in time; only the loaded-machine
worst case improves. The fix lives in the shared helpers and the readiness call sites,
so it covers all of the suite's server instances at once. It pays down what undermined
verification during M46 through M48, where a flaky pass forced repeated reruns.

## Background: what is already in place

- **`waitgrep`.** The one polling primitive: `grep -q` for a pattern in a file, retried
  sixty times at fifty milliseconds, so three seconds total, then a nonzero return.
- **The readiness gates.** At each server the suite waits for `admin invite:` (or
  `world signing on`) in the server log, then connects an SSE stream and waits for the
  session-id line (`^data: I`), then captures the id. There are twenty-one such waits,
  each written `waitgrep ... || true`, so a timeout is swallowed and the id capture that
  follows returns empty.
- **The empty-id cascade.** A command posts `"$SID <verb>"`; with `$SID` empty the
  server cannot route it, so it and every check that reads its result fail. A block has
  several checks, so one missed gate looks like several unrelated failures.
- **`check_log`.** The outcome check: `waitgrep` then `pass` or `fail`. It carries the
  same three-second bound as a readiness gate, though a game outcome (a fight settling,
  a reset firing) can legitimately take longer under load.
- **The nine server instances.** The main test server plus eight isolated instances
  (the history, agent, and gc tests). Each has its own readiness gates, so each is a
  separate chance for the cascade.

## Design: separate readiness from outcome, and wait long enough

Two changes, both in the shared helpers.

A readiness gate becomes its own helper with a generous bound and a loud, single
failure. It waits for the boot marker and then for the session id, retries the id
capture until it is non-empty, and if the server truly never comes up it reports one
clear failure naming the instance rather than returning empty and letting the block
melt down. The bound is long enough that a slow boot waits it out, since a poll that
succeeds returns at once and a longer ceiling costs a healthy run nothing.

An outcome check keeps its `pass`/`fail` contract but waits on a longer ceiling, so a
correct result that is merely late still passes. The ceiling is a false-failure guard,
not a typical duration, because the poll exits as soon as the pattern appears.

The principle is that a bound is there to catch a genuine hang, not to race the
machine. A genuine boot race would fail every run, which is not what is seen; the
failures are occasional and load-correlated, which is what short windows produce.

## Slice a: robust readiness gates (shipped)

Remove the empty-id cascade.

- Add a readiness helper that waits for a server's boot marker and session id on a
  generous bound, captures the id, and verifies it is non-empty, retrying until it is
  or the bound elapses.
- On a true timeout, fail once with a message naming the instance, instead of the
  `|| true` that proceeds with an empty id. Convert the twenty-one gate sites to it.

Shipped: two helpers in `test.sh` share a generous ceiling (`READY_TRIES`, 400 polls
at 50ms, so 20s). `wait_ready FILE PATTERN` replaces the nine boot-marker
`waitgrep ... || true` gates (`admin invite:` and `world signing on`); it is silent on
success, so it adds no check, and on a true timeout it emits one named `fail`.
`wait_sid PLAYER_LOG` replaces the twelve SSE-plus-capture pairs; it runs inside
`$(...)`, so it never touches the counters (a subshell cannot), and instead echoes a
non-empty session id or, on timeout, writes a stderr note and returns nonzero. The
main and player-3 blocks keep their existing `[ -n "$SID" ]` pass/fail, and the eight
isolated-instance captures gained `|| fail "no session id: <log>"`, so a genuine boot
failure is one named failure rather than a cluster of downstream ones. Because a poll
returns the instant its condition holds, a healthy run is unchanged: the suite still
reports 454 checks with the same typical time. The helper logic was unit-tested
directly: a delayed boot marker and a delayed session id are both waited out and
captured, a marker that never appears yields exactly one `fail`, and a session id that
never appears makes `wait_sid` return nonzero so the caller's `|| fail` fires exactly
once.

## Slice b: robust outcome waits

Stop late-but-correct results from failing.

- Raise `check_log`'s ceiling (and factor the poll so the readiness helper and
  `check_log` share one primitive), keeping the `pass`/`fail` semantics unchanged.
- Confirm a healthy run's wall time is unchanged, since each poll still returns on the
  first match.

Verification runs the full suite and confirms it passes with the raised ceiling, and
that a check for a result that never appears still fails within a bounded time rather
than hanging.

## Slice c: prove determinism

Make the absence of flakiness something the project can check.

- Add a documented stress mode that runs the suite several times in a row and requires
  every run clean, so a reintroduced short window is caught.
- Run a long streak of clean passes as the evidence, and document the harness timing
  model (readiness versus outcome, and why bounds are ceilings not durations) so a
  future milestone does not add a short fixed wait.

Verification is the streak itself: the suite run many times with no failure, where the
flake that motivated the milestone appeared roughly once in a dozen runs before.

## Deferred: fewer instances and a faster suite

Cutting the number of server spawns, sharing one instance across more of the isolated
tests, or parallelizing independent blocks would shrink both runtime and the flake
surface, but they change what the tests exercise and how they are isolated. They stay
deferred as a separate performance milestone, since this one is about correctness of
the pass or fail, not speed. The bounds this milestone raises are ceilings, so they do
not slow a healthy run and do not conflict with a later speed pass.

## Verification

The suite passes, a healthy run's typical time is unchanged, an artificially slow boot
is waited out rather than cascading, a server that never comes up reports one clear
failure, and a long streak of consecutive clean runs stands where the flake once
appeared about once in a dozen. The stress mode makes that streak repeatable on
demand.

## Dependencies

Depends on: the smoke-test harness itself (`test.sh`, its `waitgrep`, `check_log`,
`pass`, and `fail`), and the many milestones whose isolated server instances the
readiness helper now gates uniformly, in particular the M29-M31 history tests and the
M48 hermetic-history tests that spawn the most instances.
